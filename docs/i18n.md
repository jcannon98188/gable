# Internationalization (i18n)

Gable translates through markers you write in templates and a tag you use in code. Both resolve against a catalog of translations at runtime, and both re-render when the locale changes. The Vite plugin (`gableI18n` in `@gable/vite`) can extract messages from your sources into catalogs and bake one build per locale; this page describes the format, the runtime, and both modes.

## Marking text in templates

`i18n` on an element translates the element's text. `i18n-<attribute>` translates a static attribute. The value is a description for translators (optional) and may carry an explicit id after `@@`.

```ts
html`
  <h1 i18n="page title">Welcome</h1>
  <p i18n>Hello {{ name() }}, you have {{ count() }} messages</p>
  <input title="Search" i18n-title="search field" placeholder="Name" i18n-placeholder />
  <button i18n="save button@@save">Save</button>
`;
```

Rules:

- `i18n` marks the element's own text: static text plus `{{ }}` interpolations. The element may not contain other elements (put `i18n` on those instead), and no other text in the template is translated.
- Each `{{ expression }}` becomes a placeholder in the message: `{0}`, `{1}`, ... in order of appearance. The expression is still evaluated by Gable; translators only see the placeholder and can reorder it.
- `i18n-title` needs a static `title="..."` next to it. Bindings such as `[title]="x"` are not translatable here; produce the value with the `i18n` tag in code.
- Whitespace in a message is collapsed and trimmed, so reformatting the template does not change the message.
- `i18n`, `i18n-*` and their values are not rendered into the DOM.
- Templates have no `${}` holes, so `${}` only appears in the `i18n` tag for code (below).

The attribute value is `description`, `description@@id`, `@@id` or empty:

| Marker | Description | Id |
| --- | --- | --- |
| `i18n` | none | derived |
| `i18n="page title"` | `page title` | derived |
| `i18n="page title@@title"` | `page title` | `title` |
| `i18n="@@title"` | none | `title` |

## Message ids

A message's id is how a catalog finds it. By default it is derived, so a catalog entry is tied to the exact text and description it was extracted from:

```
id = hex16( fnv1a64( utf8( message + "\0" + description ) ) )
```

`message` is the extracted source message (placeholders as `{0}`, `{1}`..., whitespace collapsed, literal `{`, `}` and `\` escaped with a backslash); `description` is the marker's description, or empty. The result is 16 lowercase hex digits. Changing the text or the description changes the id, which is the point: translations are not silently reused for a different meaning, and the same words with different descriptions ("Open" the verb, "Open" the status) get separate entries.

Use an explicit `@@id` when an id must survive edits to the text. `messageId(message, description)` computes the derived id; it is exported from `@gable/core/i18n` (and `@gable/core/tooling`) and is the only implementation, so the runtime, the language service and the extractor always agree.

## Messages in code

`i18n` is a tagged template. Call it in a field initialiser; it returns a signal of the current text that follows the locale and any signals in the holes (a hole holding a zero-argument function is called, which is what a signal is).

```ts
import { i18n, signal } from '@gable/core';

class Inbox {
  count = signal(3);
  title = i18n`Inbox (${this.count})`;       // {{ title() }} in the template
  state = i18n`:mailbox state@@state:Ready`; // :description@@id: prefix
}
```

To get a plain string at a point in time (inside a computed, an event handler, a router title) inject `I18n` and use its `t` tag. Read inside a computed or effect it is reactive; anywhere else it is just the current text.

```ts
import { computed, inject, I18n } from '@gable/core';

class Cart {
  #i18n = inject(I18n);
  label = computed(() => this.#i18n.t`${this.items()} items`);
}
```

## Message syntax

Messages use an ICU-style syntax, formatted with `Intl.PluralRules`, `Intl.NumberFormat` and `Intl.DateTimeFormat` for the active locale.

| Form | Example |
| --- | --- |
| Placeholder | `Hello {0}`, `Hello {name}` |
| Plural | `{0, plural, =0 {No items} one {# item} other {# items}}` |
| Plural with offset | `{n, plural, offset:1 =0 {nobody} one {you and # other} other {you and # others}}` |
| Ordinal | `{n, selectordinal, one {#st} two {#nd} few {#rd} other {#th}}` |
| Select | `{who, select, female {She} male {He} other {They}} left` |
| Number | `{0, number}`, `{0, number, percent}`, `{0, number, integer}`, `{0, number, compact}`, `{0, number, currency:EUR}` |
| Date and time | `{0, date}`, `{0, date, long}`, `{0, time, short}` (`short`, `medium`, `long`, `full`) |

- Plural and select need an `other` branch. In a plural, `#` is the number (minus any offset), formatted for the locale. Branches may nest and may contain placeholders.
- A plain `{0}` prints `String(value)`; use `{0, number}` for locale formatting.
- Escape a literal `{`, `}`, `#` or `\` with a backslash: `\{`, `\}`, `\#`, `\\`. (This is deliberately not ICU's apostrophe quoting, so "don't" needs no care.)
- The source text of a template message is plain text with placeholders. Write plural and select forms in the translation, referring to the placeholder by number: the English `{{ count }} items` is the message `{0} items`, and the French catalog entry is `{0, plural, one {# objet} other {# objets}}`. The same holds for the `i18n` tag in code: its text is literal (braces are escaped for you); plural forms live in the translations.

## Catalogs

A catalog is a JSON object from message id to translated message. Either shape is accepted:

```json
{
  "locale": "fr",
  "translations": {
    "92251de07c5a32d1": "Bienvenue",
    "save": "Enregistrer",
    "3c5a10f4d6a0b1e2": "{1, plural, one {# message} other {# messages}} pour {0}"
  }
}
```

```json
{ "92251de07c5a32d1": "Bienvenue" }
```

Translators may reorder placeholders, drop or repeat them, and use any ICU form around them. A translation that fails to parse is reported and the source text is shown instead.

Extraction (build tooling) produces the source catalog and the file translators work from. `@gable/core/tooling` exports everything the Vite plugin needs, all DOM-free:

- `extractTemplateMessages(templateSource, { file, firstLine })` returns `{ id, message, description, placeholders, location }` for every marker in a template, using the runtime's own parser.
- `messageFromStrings(strings)` builds the message and marker of an `i18n` tagged template call.
- `mergeExtracted(messages)` joins results by id (first wins, locations are merged) and reports two different messages claiming one explicit id.
- `sourceCatalogJson(messages, sourceLocale)` writes the source-language catalog.
- `toXliff(messages, { sourceLocale, targetLocale, translations })` and `fromXliff(xml)` exchange XLIFF 1.2 with translation tools. Descriptions, locations and placeholder hints become `note` elements; `fromXliff` reads each `trans-unit`'s `target`.
- `formatMessage`, `parseMessage`, `readCatalog`, `parseMarker`, `messageId`.

## The `I18n` service

`I18n` is root-scoped, so `inject(I18n)` works anywhere. It works with no setup (locale `en`, no catalogs); configure it with `provideI18n`:

```ts
import { bootstrap, provideI18n } from '@gable/core';

bootstrap(Root, {
  renderer,
  target: "#app",
  providers: [
    provideI18n({
      sourceLocale: 'en',        // the language your templates are written in (default 'en')
      locale: navigator.language,
      catalogs: { fr },           // known up front
      loader: (locale) => import(`./locales/${locale}.json`), // loaded on demand by setLocale
    }),
  ],
});
```

| Member | |
| --- | --- |
| `locale` | Signal of the current locale. |
| `setLocale(locale)` | Loads the catalog through the loader if it is not registered, then switches. The old locale stays until the new one is ready. Rejects if loading fails. |
| `register(locale, catalog)` | Adds a catalog synchronously; text already on screen updates. |
| `load(locale)` | Loads and registers without switching (for preloading). |
| `translate(id, source, args)` | The primitive the markers use. |
| `t` | Tag form of `translate`. |
| `missing` | Missing translations seen so far (dev builds). |

Lookup tries the full locale then shorter forms: `zh-Hant-TW`, `zh-Hant`, `zh`. A message with no translation shows its source text. In dev builds the first such miss for each locale and id logs `[gable] i18n: no translation for fr (id ...)`; pass `onMissing` to `provideI18n` to collect them instead. Nothing is reported while the locale is the source locale (or a variant of it, such as `en-GB`). Production builds (`__GABLE_DEV__` false) skip the check.

## Testing

`mount` and `mountApp` take an `i18n` option with the same fields as `provideI18n`, and the fixture exposes the service as `fixture.i18n`. Missing translations are collected in `fixture.i18n.missing` instead of logged.

```ts
import { messageId } from '@gable/core/i18n';
import { mount } from '@gable/testing';

const f = mount(Greeting, {
  i18n: { locale: 'fr', catalogs: { fr: { [messageId('Welcome', 'page title')]: 'Bienvenue' } } },
});
expect(f.textOf(f.query('h1')!)).toBe('Bienvenue');

await f.i18n.setLocale('en');
await f.flush();
```

## Editor and CLI checks

The language service (`gable-check` and the editor plugin) reports marker mistakes:

| Rule | Default | Reports |
| --- | --- | --- |
| `i18n-attr-missing` | error | `i18n-title` with no static `title="..."` on the element. |
| `i18n-not-translatable` | error | `i18n-title` next to a `[title]` binding; `i18n` on an element that contains other elements or blocks. |
| `i18n-marker-syntax` | error | A malformed marker value, such as an empty id (`"text@@"`). |
| `i18n-empty` | warn | `i18n` on an element with no text, or with only `{{ }}` interpolations and nothing to translate. |
| `i18n-missing-translation` | warn | A marked message that a configured locale's catalog has no translation for. Needs the `i18n` option (below); does nothing without it. |
| `i18n-unmarked-text` | off | User-facing static text that is not marked for translation. Opt in with `"i18n-unmarked-text": "warn"`. |

Configure them under `rules` like the accessibility rules. The runtime rejects the first two cases (and `i18n` on elements with element children) with an error when the template is first built.

### Missing translations

Give the `@gable/language-service` entry in `tsconfig.json` an `i18n` section, the same shape as the options of `gableI18n` (extra keys such as `bake` are accepted and ignored, so one object can serve both):

```json
{
  "compilerOptions": {
    "plugins": [
      {
        "name": "@gable/language-service",
        "i18n": { "sourceLocale": "en", "locales": ["fr", "de"], "catalogs": "src/locales/messages.{locale}.json" },
        "rules": { "i18n-missing-translation": "warn" }
      }
    ]
  }
}
```

`catalogs` is relative to the tsconfig's folder and defaults to the path above; `.xlf` selects XLIFF. The source locale is never checked. The rule reads each locale's catalog (JSON or XLIFF; a message counts as translated when its id has an entry in `translations`, or a `<target>` in XLIFF), and reports each marked message at its `i18n` or `i18n-<attribute>` marker with the locales it lacks: `"Search" (id 8bd803ecc83852a3) has no translation for fr, de`. A locale with no readable catalog file is reported for every message, with a note. Catalogs are re-read when they change on disk, so editors pick up new translations. Without an `i18n` section the rule is off. It checks `html` templates, `i18n` tagged templates and `.t` tagged templates on the I18n service (`inject(I18n).t`, or a receiver whose name contains `i18n`, the same spelling the Vite plugin extracts) in TypeScript files, using the same message and id as the extractor; the diagnostic sits on the tag (``i18n`Inbox ${n}` ``).

### Unmarked text

`i18n-unmarked-text` (off by default) flags what a translator would never see:

- static text with letters in a template that is not inside an `i18n` element;
- a static `title`, `placeholder`, `alt` or `aria-label` with letters and no matching `i18n-<attribute>`.

It ignores whitespace, text of numbers and punctuation only (`42 / 100 %`), text that is only `{{ }}` interpolations, and the text of `<code>`, `<pre>`, `<kbd>`, `<samp>`, `<script>` and `<style>`. Put `i18n-ignore` on an element to leave it and everything inside it alone (brand names, code samples, text that is not for people). `i18n-ignore` takes no value, is not rendered into the DOM, adds no message and is removed from baked output.

```ts
html`
  <h1 i18n>Welcome</h1>
  <p i18n-ignore>Acme Inc</p>       <!-- left alone -->
  <p>Unmarked sentence</p>          <!-- flagged -->
`
```

## The Vite plugin: two modes

`gableI18n` (from `@gable/vite`) sits next to `gable()`:

```ts
// vite.config.ts
import { defineConfig } from "vite";
import { gable, gableI18n } from "@gable/vite";

export default defineConfig({
  plugins: [
    gable(),
    gableI18n({
      sourceLocale: "en",
      locales: ["fr", "de"],
      catalogs: "src/locales/messages.{locale}.json", // the default; ".xlf" selects XLIFF
      extract: true,                                   // write and update the catalogs at the start of a build
      bake: { onMissing: "error" },                    // omit for runtime-only i18n
    }),
  ],
});
```

| Option | |
| --- | --- |
| `sourceLocale` | Language the templates are written in. Default `en`. |
| `locales` | Target locales. |
| `catalogs` | Catalog path template relative to the project root; `{locale}` is replaced. A `.xlf` or `.xliff` extension means XLIFF 1.2, anything else the JSON format above. |
| `xliff` | Optional extra path template: also write an XLIFF export per locale for translation tools. |
| `extract` | `true` (default) extracts at the start of a build; `{ dirs, serve }` sets the folders scanned (default `["src"]`) and `serve: true` also extracts when the dev server starts; `false` turns it off. |
| `bake` | `false` (default), `true`, or `{ onMissing, stripRuntime, htmlLang }`. |

Both modes read the same markers and the same catalogs, so you can start with the runtime and add baking later without touching the templates.

### Runtime mode (default)

Do nothing: ship the catalogs you want (`provideI18n({ catalogs, loader })`) and switch locale with `setLocale`. The plugin only helps with extraction in this mode. The dev server always uses this path: in `vite` (serve) `gableI18n` never transforms code, so markers render through the `I18n` service, locale changes are live, and HMR behaves exactly as without the plugin. The only thing it does in serve is the optional extraction on start (`extract: { serve: true }`).

### Extraction

Extraction scans every `.ts`, `.tsx`, `.js` and `.mjs` file under `dirs` (skipping `node_modules`, declaration files and `*.test.*`/`*.spec.*`) for `html` templates with markers, `i18n` tagged templates and `.t` tagged templates on the I18n service (see below), using the same parser and id function as the runtime. It then:

- writes the source catalog (`catalogs` with `{locale}` = `sourceLocale`);
- updates each target locale's catalog without losing work. A JSON catalog is `{ "locale", "translations", "untranslated", "obsolete" }`. `translations` holds real translations only. `untranslated` lists new messages with their source text for the translator and is recomputed on every run. `obsolete` keeps translations whose message left the source, and brings them back if the message returns. An XLIFF catalog has a `<target>` only on translated units;
- optionally writes the XLIFF export (`xliff`);
- logs how many messages are untranslated or obsolete per locale.

Descriptions, `file:line` locations and placeholder expressions (`{0} = user.name`) travel as notes in XLIFF. Files are only rewritten when their content changes. Programmatic use: `extractProject(root, dirs)` and `writeCatalogs(messages, options)` are exported from `@gable/vite`.

A workflow: run a build (or `vite` with `extract: { serve: true }`), hand `messages.fr.json` (or the `.xlf`) to the translator, and move each finished entry from `untranslated` to `translations` (XLIFF tools do this by filling `<target>`).

### Baked mode

With `bake` on, `vite build` emits one complete output per locale, `dist/en/`, `dist/fr/`, `dist/de/` (under your `build.outDir`; the source locale is included, with the markers stripped), each built as its own Vite environment:

- Static text of every `i18n` element and every `i18n-<attr>` attribute in an `html` template is replaced by the translation, and the markers are removed. Placeholders are honoured: the source `Hello {{ name() }}, you have {{ count() }} messages` with the French `{1} messages pour {0}, bonjour` becomes `<p>{{ count() }} messages pour {{ name() }}, bonjour</p>`, still bound to the same expressions.
- An `i18n` tagged template becomes a `computed` of a plain template literal with the holes placed as the translation orders them (signals in holes are still read, so the value stays reactive).
- A `.t` tagged template on the I18n service (``inject(I18n).t`Saved` `` or ``this.#i18n.t`${n} items` ``) becomes a plain template literal in the same way, with the same extraction. The receiver is recognised by its spelling: `inject(I18n)`, or a name that contains `i18n` (`i18n`, `this.i18n`, `this.#i18n`, `i18nService`). Anything else named `.t` is left alone.
- A call that is not a tagged template (`i18n.t(parts, x)`, `i18n.translate(id, source, args)`) is dynamic: it stays a runtime lookup, is not extracted, and the plugin warns with its `file:line` once per call during a baked build. Keep the runtime for it, or rewrite it as a tagged template.
- `<html lang>` of each output's `index.html` is set to its locale (`<html lang="fr">`, replacing an existing `lang`). `bake: { htmlLang: false }` leaves it alone.
- Rewritten modules carry a source map (made with `magic-string`, a dependency of the plugin that Vite already ships), so the rewritten templates still map back to their source lines. Only the rewritten edits are remapped; everything else maps one to one.
- No catalog, locale switch, `I18n` service or ICU formatter ends up in the bundle: after baking nothing calls core's marker renderer, so the plugin stubs it out (`stripRuntime: false` keeps it, for dependencies that ship unbaked markers).

`i18n-ignore` attributes (the lint hint above) are dropped from baked templates.

Plural, select, selectordinal, number and date forms bake in code messages (the `i18n` tag and `inject(I18n).t`). The locale and the formats are known at build time, so each form is lowered to inline code over `Intl.PluralRules`, `Intl.NumberFormat` and `Intl.DateTimeFormat`: a plural becomes a small arrow function that picks the branch (exact `=n` matches first, then the plural category, then `other`), `#` becomes the locale-formatted number, and nested forms and placeholders work. Each module that needs it gets a few lines of helpers (`__gablePlural`, `__gableNum`, `__gableDate`) and nothing else: no ICU parser, no `I18n` service, no catalog in the bundle. The output behaves like the runtime formatter for the same message.

Forms in `html` templates (an `i18n` element or an `i18n-<attribute>`) cannot be baked, and a translation using them fails the build with a message naming the id. This is a deliberate limit: templates cannot call functions, so each plural would have to become a synthesised `computed` field on the class, rewriting the component's code as well as its template, and mixed content (a plural branch containing other placeholders) makes that worse. Use the runtime mode for those messages, or produce the text with the `i18n` tag in code and bind it (`{{ label() }}`). Baked templates and attributes take plain placeholders (`{0}`, `{1}`, escapes) only, and translations may not contain `<` or `{{` in templates.

Missing translations are set by `bake.onMissing`:

| Value | Behaviour |
| --- | --- |
| `"error"` (default) | The build fails, listing every missing message with its id and `file:line`. |
| `"warn"` | A warning per message; the source text is used. |
| `"source"` | The source text is used silently. |

The source locale never has missing translations. A locale with no catalog file is always an error.

Notes and limits:

- Mark whole sentences. Baking replaces an element's text as a unit, so fragments cannot be reordered across elements.
- html templates with markers may not contain backslash escapes, and the tags must be spelled `html` and `i18n` (not aliased or called as methods).
- Hosting and routing by locale (`/fr/`) are out of scope.
