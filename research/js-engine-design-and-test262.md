# JS engine design prior art and test262 mechanics (TASK-99.10)

Question: what does the prior art say a from-scratch, Rust-written JavaScript engine must decide (bytecode and interpreter, object model and shapes, garbage collection, performance without a JIT, host-object and embedding APIs, inspector and debugging, hot-update hooks)? How do Rust engines (Boa, Nova, others) approach these, what are their conformance and performance results, and how is test262 run with feature filtering? Facts and comparison only; no decision.

Builds on `research/embeddable-js-engines` (TASK-99.2); the engine survey, Boa/QuickJS-NG basics, per-engine inspector and hot-update facts, V8 `--jitless` costs and platform tables are not repeated here. Pure-Rust portability to macOS and Android is the constraint from TASK-99, so Rust engines are the focus.

All sources fetched 2026-11-07. Almost every page was read through a summarising fetch, so none of it is verbatim-checked; statements marked "(raw)" were read from a raw file or JSON via a tool that returned structured data (the CDP protocol JSON was parsed locally). Anything not found in a primary source is under "Gaps". Inferences are labelled as such.

## 2. Bytecode and interpreter design

### Boa (docs/vm.md, docs/bytecompiler.md in repo, summary)
- Value stack: single `Vec<JsValue>` shared by all call frames; locals addressed as registers offset from a register pointer `rp`; callee allocates `register_count` slots, initialised to `undefined`.
- Encoding: one-byte opcode followed by operands; most operands are `VaryingOperand` encoded as u8, u16 or u32 depending on value. Over 100 opcodes, generated by one `generate_opcodes!` macro producing the `Opcode` enum, a decoded `Instruction` enum, a 256-entry dispatch table and emit methods.
- Frames: `CallFrame` holds `code_block`, `pc`, `rp`, `argument_count`, `env_fp`, `environments`, `realm`, with flags (`EXIT_EARLY`, `CONSTRUCT`, `REGISTERS_ALREADY_PUSHED`, `THIS_VALUE_CACHED`). Generators resume by pushing the saved frame back with registers reused.
- Environments: per-frame `EnvironmentStack`; `PushScope`/`PopScope`/`PushObjectEnvironment`; catch handlers truncate environments to `env_fp + handler.environment_count`.
- Compiler: single pass over `boa_ast` straight to a `CodeBlock` (instructions, constants vector, bindings, handler table), jump patching, a `RegisterAllocator`, separate `variable_scope` and `lexical_scope`, `BindingLocator` for resolution. Async and generators are not lowered to state machines; the compiler emits handler metadata and suspend/resume points, and the VM pauses frames at `await`/`yield`.
- Blog "How ECMAScript Engines Optimize Your Variables" (2025-03-05) exists on boajs.dev; fetch failed, content not read.

### Nova (ARCHITECTURE.md, nova_vm/src/engine/README.md, summary)
- "Nova's VM is a stack-based bytecode interpreter"; bytecode is high-level with ES-specific instructions. `Vm` state: instruction pointer, result register, reference register, stacks for values, references, exception handlers and iterators.
- A new `Vm` is created on the native stack per function call (README calls this "historical" and something that "ought to be fixed"). `Vm::execute` returns `Return`, `Throw`, `Await` or `Yield`; the last two carry a suspended `Vm` to be stored on the heap.
- Instruction format: one opcode byte plus 2 or 4 data bytes, unaligned. The dispatch loop `Vm::inner_execute` is where GC can be triggered.
- Closures are recompiled on every use because bytecode is stored per function instance (flagged by the author as a problem).
- README: interpreter performance is a goal "but not yet a high priority"; the engine is "not fast by any means".

### Brimstone (README, summary)
- Bytecode VM modelled on V8 Ignition (and V8/LibJS design influence). Details not read.

### Reference points from non-Rust engines (primary posts)
- V8 Ignition (v8.dev/blog/ignition-interpreter): register machine with an accumulator register as implicit input and output; bytecode "between 50% to 25% the size of the equivalent baseline machine code"; about 5% less memory per Chrome tab in early experiments; handlers generated from TurboFan's macro-assembler rather than hand-written assembly or C++.
- Hermes (doc/Design.md, static_h branch): register-based bytecode with up to unlimited registers, most instructions take 8-bit register indexes; linear-scan allocation on IR; fixed operand widths per opcode (more opcodes, cheaper decoding); constants loaded via dedicated opcodes; non-local variables addressed by compile-time scope-chain delta and index; bytecode file has header, function table, uniqued string table.
- QuickJS (bellard.org/quickjs/quickjs.html): "A stack-based bytecode was chosen because it is simple and generates compact code"; compiler emits bytecode directly with no intermediate representation; per-function maximum stack size computed at compile time so no runtime stack-overflow checks are needed.
- JavaScriptCore (webkit.org/blog/10308): the LLInt interpreter "obeys JIT ABI", is written in a portable assembler (offlineasm) that "can be compiled to C++", allows running JS when JIT is unavailable ("mini mode"), is designed so bytecode can be mapped from disk, and collects value profiles and inline-cache metadata used by the JIT tiers. Tier-up thresholds quoted: 500 points LLInt to Baseline, 1000 Baseline to DFG, 100000 DFG to FTL; call adds 15, loop iteration adds 1.

## 3. Object model and shapes

- Boa (docs/shapes.md, summary): shapes form a transition tree from a root shape with no prototype; each shape records prototype and property count; adding a property creates a successor shape (weak forward pointers so unused shapes can be freed); objects with the same add order share shapes; conflicting layouts fork the property table. `PropertyTable` maps keys to slot indexes; data properties take one slot, accessors two; values live in the object's dense storage, not the shape. Deleting replays later transitions from the parent shape. The doc did not describe inline caching or shared-vs-unique shapes, but the `$boa.shape.type(object)` debug function reports "shared or unique" (docs/boa_object.md), so both kinds exist. `$boa.object.indexedStorageType` reports dense or sparse element storage.
- Nova (heap/README.md, summary): ordinary object data in its own vector; most arrays "avoid creating the object base entirely"; named properties and prototype changes treated as the uncommon case; shapes mentioned only as an optimisation that would make keys "secondary". README lists no sparse array storage as a known gap.
- V8 (v8.dev/blog/fast-properties): HiddenClass (map) holds property count, prototype, descriptor array; transition tree; in-object vs out-of-object properties; dictionary ("slow") mode after many adds/deletes, where inline caches do not work; indexed properties do not create new hidden classes. IC states are not described in that post.
- JSC: structures are hash-consed so a shape check is one pointer compare; inline-cache metadata is stored per `get_by_id` in the LLInt (cached structure ID plus offset), described as "negative cost profiling"; watchpoints let the compiler assume invariants and be notified when they break.
- Hermes Design.md did not cover its object model.

## 4. Garbage collection

| Engine | Approach | Source |
|---|---|---|
| Boa | `boa_gc` mark-sweep; `Gc<T>`, `GcRefCell` (dynamic borrow checks), `WeakGc`, `WeakMap`, `Ephemeron`, derivable `Trace`, `Finalize` as `Drop` substitute; docs list only `force_collect`, no stated automatic trigger policy | docs.rs/boa_gc (summary) |
| Nova | Compacting mark-and-sweep with moving values; GC may run in any function that takes a `GcScope`; `Value` handles are unrooted and invalid after a collection; `Scoped<Value>` roots them in a scoped list (index stable across collections); `NoGcScope`/`GcScope::reborrow` make misuse a compile error; scoping the same value twice stores it twice and creating a `Scoped` can allocate | GARBAGE_COLLECTOR.md (summary) |
| Brimstone | Compacting, "very unsafe Rust" | README (summary) |
| QuickJS | Reference counting (deterministic frees) plus a separate cycle-removal pass "when the allocated memory becomes too large"; cycle pass uses only refcounts and object contents so C code needs no explicit roots; `JS_SetMemoryLimit`, custom allocator via `JS_NewRuntime2`, per-class `gc_mark` hook | quickjs.html (summary) |
| V8 | Generational: semi-space scavenger for young generation, mark-sweep-compact for old; parallel, incremental and concurrent phases; "the work here is not finished" | v8.dev/blog/trash-talk (summary) |
| Kiesel | bdwgc (conservative C collector) | README (summary) |

Nova's heap arenas are compacted, so a 32-bit handle plus type selects a vector and index (heap/README.md); Boa uses Rust `Gc` pointers. Nova README states `GcAgent::new` and `run_in_realm` receive a GC scope, i.e. rooting is part of the embedder API.

## 5. Performance without a JIT

- Boa benchmarks page (boajs.dev/benchmarks, summary): V8 benchmark suite V7 run nightly on GitHub Actions; higher score is better; compared engines are Boa, V8 (jitless), SpiderMonkey (jitless), Kiesel, Porffor (AOT, flagged as not like-for-like), Duktape, QuickJS. The page text contained no numeric scores, so no figures are available from this fetch. Boa README gives no timings either.
- Boa: `--optimize` flag exists on the test262 runner (`OptimizerOptions::OPTIMIZE_ALL`); `$boa.optimizer` exposes `constantFolding` and `statistics`.
- Nova: no benchmarks published; README says performance is acceptable but "not fast by any means" and that code with `as any`/`as unknown` types will be slower and heavier.
- Earlier research already holds V8 `--jitless` cost figures and QuickJS vendor claims; see TASK-99.2.
- JSC documents the LLInt as a no-JIT execution mode (see section 2), including inline-cache metadata in the interpreter.
- Common techniques named in primary sources for non-JIT speed: compact bytecode (V8, Hermes, QuickJS), register machines with accumulator or fixed operand widths (V8, Hermes), compile-time scope resolution to slot indexes (Hermes), inline caches over shapes in the interpreter (JSC), opcode fusion and polymorphic inline caching (QuickJS-NG docs, per TASK-99.2; no figures).

## 6. Host-object and embedding APIs

- ECMA-262 16th edition (June 2025, ES2025) lists host-defined operations by section (from the TOC; purposes inferred from titles, definitions not read): HostMakeJobCallback (9.5.2), HostCallJobCallback (9.5.3), HostEnqueueGenericJob (9.5.4), HostEnqueuePromiseJob (9.5.5), HostEnqueueTimeoutJob (9.5.6), HostEnqueueFinalizationRegistryCleanupJob (9.9.4.1), HostEnsureCanAddPrivateElement (7.3.29), HostGetImportMetaProperties (13.3.12.1.1), HostFinalizeImportMeta (13.3.12.1.2), HostLoadImportedModule (16.2.1.10), HostEnsureCanCompileStrings (19.2.1.2), HostHasSourceTextAvailable (20.2.5). HostPromiseRejectionTracker was not located in the portion read.
- Boa: add `boa_engine`, create `Context::default()`, call `context.eval(Source::from_bytes(..))`. Native objects: types implement `JsData` (marker) plus `Any` and `Trace`; stored in `ObjectData<T>` aligned to 8 bytes (larger types must be boxed); created with `JsObject::from_proto_and_data`; accessed with `downcast`, `downcast_ref`, `downcast_mut`, `borrow_mut` (docs/native_object.md, summary). Companion crates `boa_runtime` (Web APIs), `boa_icu_provider`, `boa_interner`, `boa_parser`, `boa_ast`. Wasm target supported (`js` feature on wasm32-unknown-unknown).
- Nova: `GcAgent::new(Default::default(), &DefaultHostHooks)`, `create_default_realm()`, `run_in_realm(agent, gc_scope)`; the `Agent` is "the only pointer passed consistently through call stacks"; strings are WTF-8 internally.
- QuickJS (C API): refcounted `JSValue`, explicit `JS_DupValue`/`JS_FreeValue`, no implicit stack, classes with finalizers and `gc_mark`, interrupt handler for timeouts (see also TASK-99.2 for NG's module loader and promise rejection tracker hooks).

## 7. Inspector and debugging support

- Boa (docs/debugging.md, docs/boa_object.md, summary): CLI `--dump-ast`, `--trace` (bytecode plus executed instructions), `--flowgraph` (Graphviz or Mermaid); `$boa` object (needs `--debug-object`) with `gc.collect()`, `function.bytecode/trace/traceable/flowgraph`, `object.id/indexedStorageType`, `realm.create()`, `shape.id/type/same`, `limits.loop/stack/recursion/backtrace`, `string.storage/encoding/summary`. "The page does not mention a programmatic debugger API"; interactive debugging is via CodeLLDB on the Rust process.
- Nova: no inspector information found in the files read.
- Chrome DevTools Protocol, Debugger domain, version 1.3 (parsed from `js_protocol.json`, raw): commands include `enable`, `disable`, `pause`, `resume`, `stepInto`, `stepOver`, `stepOut`, `continueToLocation`, `setBreakpoint`, `setBreakpointByUrl`, `setBreakpointOnFunctionCall` (experimental), `removeBreakpoint`, `getPossibleBreakpoints`, `setBreakpointsActive`, `setPauseOnExceptions`, `evaluateOnCallFrame`, `restartFrame`, `setVariableValue`, `setReturnValue` (experimental), `getScriptSource`, `searchInContent`, `setAsyncCallStackDepth`, `setBlackboxPatterns`/`setBlackboxedRanges` (experimental), `setInstrumentationBreakpoint`, `setSkipAllPauses`, `getStackTrace` (experimental). Events and the Runtime/Profiler/HeapProfiler domains are separate and were not enumerated.
- A CDP implementation therefore needs, from the engine: source positions per bytecode offset (for `getPossibleBreakpoints`/`setBreakpoint`), pause and step hooks in the interpreter loop, access to frame locals and scopes (for `evaluateOnCallFrame`, `setVariableValue`), script identity and source retrieval, and async stack tracking. This list is inferred from the command set, not stated by a source.

## 8. Hot-update hooks

- CDP `Debugger.setScriptSource` is marked `deprecated`, with the description "Live edit is no longer supported and this command always fails with a 'no longer available' error." (raw JSON). So the standard debugger protocol no longer offers engine-side live edit.
- Spec-level hooks usable for module replacement are the module host hooks in section 6 (HostLoadImportedModule, HostGetImportMetaProperties, HostFinalizeImportMeta); the spec has no module unload or re-evaluate operation (not verified by a primary quote here; TASK-99.2 and `research/hmr-prior-art` hold HMR facts).
- Engine-side primitives from earlier research: precompiled bytecode load (QuickJS `JS_ReadObject`, Hermes `.hbc`, V8 code cache), multiple contexts or realms per process. Boa exposes `$boa.realm.create()` and `$262.createRealm` provides a spec-level new-realm primitive; Nova exposes `create_default_realm()`.
- Nova notes closures recompile bytecode on every use (section 2), which bears on any scheme that swaps function bodies at runtime (inference, not a source statement).
- No Rust engine README or doc read describes an update/HMR API.

## 9. test262 mechanics

### Repository layout and files
- `test/` has six subdirectories: `annexB`, `built-ins`, `harness`, `intl402`, `language`, `staging` (directory listing, raw). `harness/` holds support files (33 listed, including `assert.js`, `sta.js`, `doneprintHandle.js`, `propertyHelper.js`, `compareArray.js`, `asyncHelpers.js`, `atomicsHelper.js`, `temporalHelpers.js`, `testIntl.js`, `testTypedArray.js`, `wellKnownIntrinsicObjects.js`, `features.yml`, plus an `sm` subdirectory).
- Test runners are volunteer-maintained and are listed in the test262 README; Node-based `tc39/test262-harness` is one. Rules for running tests are in `INTERPRETING.md`.

### How a test must be interpreted (INTERPRETING.md, summary)
- Frontmatter: `includes` (harness files evaluated in listed order, after test262-defined bindings and the async file), `flags`, `features`, `negative` (`phase`: `parse`, `resolution` or `runtime`; `type`: error constructor name), `locale`, `esid`, `info`.
- Flags: `onlyStrict`, `noStrict`, `module`, `raw`, `async`, `generated` (informational), `CanBlockIsFalse`, `CanBlockIsTrue`, `non-deterministic`.
- Strict handling: unless `noStrict`, `onlyStrict`, `module` or `raw`, every test runs twice, the second time with `"use strict";` prepended as the first characters plus a newline. `raw` tests get no harness and run once, non-strict. `module` tests run once as module code; specifiers start `./`; files with `_FIXTURE` in the name are not standalone tests; `.json` files are JSON modules.
- Harness: `assert.js` and `sta.js` are evaluated in the test realm before every non-raw test; `doneprintHandle.js` is added for async tests. Each test runs in a new realm.
- Async protocol: the test calls `print('Test262:AsyncTestComplete')` on success or `print('Test262:AsyncTestFailure:...')` on failure; the runner chooses a timeout.
- Pass criterion: no uncaught exception, unless the test is negative (fail if it completes without error, throws a different constructor name, or throws in a different phase) or async. `$DONOTEVALUATE()` is runner-defined and used only in negative tests.
- Required host surface: global `print`; `$262.createRealm`, `evalScript`, `detachArrayBuffer`, `gc` (must throw if unsupported), `global`, `IsHTMLDDA` (only on supporting hosts, tagged by the `IsHTMLDDA` feature), `AbstractModuleSource`, and `$262.agent` (`start`, `broadcast`, `getReport`, `sleep`, `monotonicNow`; inside agents `receiveBroadcast`, `report`, `sleep`, `leaving`, `monotonicNow`) for SharedArrayBuffer/Atomics tests.

### Feature filtering
- `features.txt` (raw, summarised) is the list of valid `features` values; the header says tests of new features should carry a feature flag, but the file does not label features by ECMAScript edition year and does not mark any as excluded. At fetch it had 199 entries: 17 "proposed" (stage 3), 180 "standard" (kept "largely for historical reasons"), 2 test-harness features (`IsHTMLDDA`, `host-gc-required`). Proposed entries included: `Intl.Era-monthcode`, `Intl.Locale-info`, `Intl.NumberFormat-v3`, `legacy-regexp`, `ShadowRealm`, `decorators`, `source-phase-imports`, `source-phase-imports-module-source`, `import-defer`, `export-defer`, `import-text`, `immutable-arraybuffer`, `import-bytes`, `nonextensible-applies-to-private`, `await-dictionary`, `error-stack-accessor`, `Iterator.prototype.join`. Standard section includes `Temporal`, `Float16Array`, `explicit-resource-management`, `RegExp.escape`, `Math.sumPrecise`, `Error.isError`, `upsert`, `Array.fromAsync`, `tail-call-optimization`, `Atomics.pause`, `Atomics.waitAsync`, `canonical-tz`, `caller`, `__proto__`, `__getter__`, `__setter__`, `u180e`. (Whether `upsert`, `Temporal` etc. are actually in ES2025 was not checked; the list is by file section, not by edition.)
- Consequence stated by the layout (inference): an edition cut such as "ES2025" has no field in test262; runners build it themselves from feature names plus a pinned test262 commit. Boa does exactly that, see below.
- `test/staging/` (CONTRIBUTING.md, summary): "tests that are subject to fewer requirements, in order to get tests running across more than one implementation as early as possible"; need not be one test per file or follow a style; must cover an existing feature, a Stage 3 proposal or a normative pull request; staging tests "do not count towards the test262 coverage requirement for a TC39 proposal to reach Stage 4"; tests needing ECMA-402 go in `test/staging/intl402/`. The `features` key is required for new tests of new features but missing keys do not block contributions. `test/annexB` is not described in the files read.
- test262-harness options (README, summary): `--host-type` (via eshost; default `node`), `--host-path`, `--host-args`, `-t/--threads`, `-r/--reporter` (`json` or `simple`), `--reporter-keys`, `--test262-dir`, `--includes-dir`, `--tempDir`, `--prelude` (repeatable), `--timeout` (default 10000 ms), `--transformer`, `--preprocessor`, `--accept-version`, `--save-compiled-tests`, `--save-only-failed`, `--error-for-failures`, and feature filters `--features-include`, `--features-exclude` ("exclusions are resolved after inclusions"), deprecated `--features`. The repo README presents itself as "Experimental harness for test262"; the Travis badge and some links still point at the older `bterlson` repository.
- QuickJS ships its own runner: `make test2`, known failures in `test262_errors.txt` (`-u` updates it), config in `test262.conf`, `-f` for a single file, test suite cloned then patched with `tests/test262.patch` (quickjs.html, summary).

### Boa's test262 runner (tests/tester/src/main.rs, test262_config.toml; summary)
- `boa_tester run` options: `--test262-path`, `--test262-commit` (`latest` updates to `origin/main`), `-s/--suite`, `-O/--optimize`, `-o/--output`, `-d/--disable-parallelism`, `-c/--config` (default `test262_config.toml`), `--edition` (maximum ECMAScript edition to test), `--versioned` (per-edition table), `--console`; `compare <base> <new> [-m]` diffs two result files.
- Flags handled as bitflags: strict, no_strict, module, raw, async, generated, can_block_is_false/true, non_deterministic; default `STRICT | NO_STRICT`; configured ignored flags skip tests.
- Feature ignoring is config-driven: the `[ignored]` section lists features by name; matching is on the full name or the part before the first `.` (for accessors such as `Intl.DurationFormat`). Committed config pins test262 commit `d86b2294eb0a17eaa281ff12c73c473ec864c72f`. Ignored features at fetch: unimplemented `symbols-as-weakmap-keys`, `Intl.DisplayNames`, `Intl.RelativeTimeFormat`, `Intl-enumeration`, `Intl.DurationFormat`, `regexp-duplicate-named-groups`, `explicit-resource-management`; pending proposals `import-bytes`, `Intl.Locale-info`, `legacy-regexp`, `import-defer`, `ShadowRealm`, `decorators`, `source-phase-imports-module-source`, `immutable-arraybuffer`, `iterator-includes`, `iterator-chunking`, `error-stack-accessor`; non-standard `caller`. 28 individual tests are ignored with reasons (OOM, 4 panics, 9 ICU4X extension canonicalisation, 3 ICU4X h24 hour cycle, 1 `formatRangeToParts`, 1 regress named-groups, 9 source-phase imports).
- Results JSON (`boa-dev/data` `test262/refs/heads/main/latest.json`, summary) for that same commit `d86b2294...` (listed field `u`): overall `t` 53,578, `o` 51,450, `i` 1,648, `p` 0 (field meanings inferred as total, passed, ignored, panics; consistent with the earlier 96.0% finding). Per-edition rows (`t`/`o`/`i`): es5 8,165/8,125/23; es6 27,680/27,459/36; es8 28,859/28,621/36; es11 36,031/35,650/115; es13 42,475/41,940/245; es14 42,882/42,261/290; es15 43,722/43,101/290; es16 (ES2025) 45,010/44,267/412; es17 45,323/44,572/420. From those rows, ES2025 passed share is 44,267 / 45,010 = 98.3% (computed here; it counts ignored tests in the denominator). Per-suite (annexB, intl402, staging) breakdown was in truncated data and not read.
- `$262` is a runner/host concern; the Boa runner file itself does not define it (it is in an `exec` module not read), while Boa's README states a `$262` host object can be injected from the CLI.

### Nova and others
- Nova README and ARCHITECTURE.md do not describe the test262 runner; the repo has `nova_cli/` and `tests/` directories. trynova.dev reports "about 80%" without date or count; there is no Nova per-edition table in what was read.
- Brimstone reports over 97% on language tests and lists SharedArrayBuffer and Atomics as unimplemented (implication: `$262.agent` tests do not run).
- Kiesel: README test262 percentage is a dynamic badge; only a stale figure (25%) appears in text.
- test262.fyi is a client-rendered page and returned no numbers in earlier research; not retried.

## 10. Conformance vs feature coverage notes from the Rust engines

- Boa gaps from its own ignore list: `explicit-resource-management`, `regexp-duplicate-named-groups`, `symbols-as-weakmap-keys`, several Intl constructors; Intl rests on ICU4X, with ICU4X limitations listed as ignored-test reasons; Temporal via `temporal_rs` (shared with Kiesel and V8 per boajs.dev blog 2025-09-24).

- Brimstone gaps: SharedArrayBuffer and Atomics; README says everything else up to ES2026 is implemented.
